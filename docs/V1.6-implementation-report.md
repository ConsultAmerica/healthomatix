# Healthomatix V1.6 — Enterprise Operations & Revenue Cycle Acceptance Report

**Version:** V1.6 — Enterprise Clinic Operations, Revenue Cycle Intelligence, Insurance Workflows & Multi-Tenant SaaS Administration  
**Date:** 2026-10-29  
**Status:** Core increments implemented locally (no commit / push / deploy)

---

## 1. Executive summary

V1.6 adds a sandbox revenue-cycle domain and a separate SaaS subscription/entitlement layer on the existing multi-tenant platform. Clinics can store synthetic insurance policies, run Fake 270/271 eligibility, capture and approve charges, build professional claims, submit to a Fake clearinghouse, import Fake 835-style remittances, maintain an append-only patient ledger, manage denials, and view RCM analytics. Healthomatix plan activation enables backend feature entitlements (including `rcm`) with idempotent usage metering. No real payer, clearinghouse, or card processor traffic occurs.

## 2. Existing functionality reused

- `Tenant` as organization; `ClinicLocation`; provider profiles/credentials/availability
- RBAC (`tenant_admin`, `staff`, `provider`, `patient`, `auditor`) — billing APIs limited to admin/staff (+ provider for insurance view)
- Platform admin tenant provision (`/api/v1/platform`)
- Audit events; clinical encounter IDs as opaque references for charges
- V1.4/V1.5 clinical and AI modules unchanged

## 3. New modules implemented

| Module | Purpose |
|---|---|
| Insurance payers & policies | Synthetic coverage with masked member IDs |
| Eligibility checks | FakeEligibilityAdapter + financial readiness |
| Encounter charges | Coding review + AI suggestion (non-authoritative) + approve |
| Claims / lines / submissions | Validation, approve, idempotent sandbox submit |
| Denials | Open → assign → resolve |
| Remittances / allocations | Sandbox payment posting |
| Patient financial transactions | Ledger source of truth for balances |
| Subscription plans / org subscriptions | Fake SaaS checkout |
| Feature entitlements | Backend `require_entitlement("rcm")` |
| Usage meter events | Idempotent by `source_event_id` |

## 4. Architecture changes

```text
Clinic RCM (tenant-scoped)          SaaS billing (platform/tenant)
Insurance → Eligibility (Fake)      Plans → Checkout (Fake)
Charges → Claims → Clearinghouse    Entitlements (backend gate)
     → Remittance → Patient ledger  Usage meters (idempotent)
```

Patient medical payments and clinic SaaS subscriptions are separate tables and APIs.

## 8. Insurance integration details

- Adapter: `FakeEligibilityAdapter` (`integrations/eligibility_port.py`)
- Conceptual X12 270/271; sandbox only
- Disclaimer always returned: verification ≠ payment guarantee
- Inactive simulation: member id ending `INACTIVE` or `0000`

## 9. Clearinghouse sandbox results

- Adapter: `FakeClearinghouseAdapter`
- Accepted vs rejected (force / claim number suffix `REJECT`)
- Acceptance ≠ payment; remittance import posts ledger separately
- Evidence: `tests/test_rcm_saas_v16.py` submit + remittance + denial paths

## 10. Payment integration results

- Patient RCM: remittance allocations + ledger (no card vault)
- SaaS: `FakeSaasBillingAdapter` checkout references only
- PCI: no raw card/CVV storage

## 11. Financial reconciliation evidence

Automated flow creates charge → claim → accepted submission → remittance → patient ledger transactions; analytics `payments_posted_cents` and `patient_ar_cents` derive from those rows.

## 12. SaaS subscription testing

- Activate `professional` enables `rcm` entitlement
- RCM APIs return `FEATURE_NOT_ENTITLED` without entitlement
- Usage meter duplicate `source_event_id` returns same event id
- Cross-tenant analytics denied (404)

## 13. Security and tenant isolation findings

- Membership + tenant_id checks on all RCM/SaaS routes
- Billing role restriction (staff/admin for claims/denials)
- Member identifiers masked on policy read
- Platform usage list requires platform admin

## 15. Known limitations

- No real X12 partner, 835 parser, or payment processor
- AR aging buckets are a sandbox snapshot (balance in 0–30 only)
- Insurance card image upload / OCR not implemented
- Billing-specific RBAC role not added (uses staff/admin)
- Institutional 837 claims out of scope
- Frontend OpenAPI client not regenerated (`apiJson`)
- Multi-location ops UI largely reuses existing location APIs

## 16. Production-readiness gaps

- BAA/trading-partner agreements for eligibility & clearinghouse
- Licensed code sets (ICD/CPT/HCPCS) management
- PCI-scoped payment processor for patient balances
- Formal AR aging methodology and clean-claim definitions
- Tenant suspend/close data-retention playbooks
- Expanded authorization matrix for billing vs clinical note access

## 17. Recommended V1.7 scope

1. Live clearinghouse/eligibility partners under contract  
2. Patient statement PDF + hosted checkout for balances  
3. Billing specialist role with note-access separation  
4. Insurance card upload with human-verified OCR  
5. Full AR aging from service dates and contractual rules
